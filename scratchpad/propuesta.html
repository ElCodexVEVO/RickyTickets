01Análisis visual

Lectura de las dos referencias antes de proponer nada.

referencia.png

  • Paleta negro carbón + dorado + blanco hueso, con fotografía de Tulum como único elemento cálido — exactamente la dirección que pediste.
  • Sidebar oscura fija con ítem activo resaltado en dorado sólido; layout de dashboard clásico (sidebar + contenido) pero con tipografía y espaciado más cuidados que un admin genérico.
  • Formulario a la izquierda + vista previa del ticket en vivo a la derecha: confirma el requerimiento de tiempo real.
  • Tarjetas de estadística inferiores con número grande, etiqueta pequeña y variación porcentual — patrón de "stat tile" que replicaremos en el Dashboard.
  • Estados con pastillas de color (verde=confirmado, ámbar=pendiente) sobre fondo claro — es la única función del verde: estado positivo, tal como pediste.

ticket-original.jpeg

  • Estructura de datos ya validada por el negocio: Name, Pick Up, Room, Drop Off, Number of People, Date, Hour, Phone/Email, Airline/Flight, Date & Time of Return, Return Time, Price — la mantenemos como base de campos del PDF.
  • Encabezado oscuro con el logo y "TULUM MEXICO" en script — lo modernizamos pero conservamos el gesto.
  • Bloque final con Meeting Points (Tulum/Cancún) y condiciones de pago — obligatorio conservarlo en el nuevo PDF.
  • Debilidades a corregir: es una captura de WhatsApp (no un documento real), sin folio, sin QR, sin estado, sin identidad de marca consistente, precio y teléfono tapados a mano.
Conclusión de diseño: usamos referencia.png como sistema visual de la aplicación completa (negro carbón / dorado / blanco / gris claro, verde solo para estados) y ticket-original.jpeg como el contenido que el PDF debe preservar, elevado a un documento A4 real con folio, QR y marca consistente.

02Arquitectura completa

SPA en React servida como sitio estático, con Supabase como backend completo (Postgres + Auth + Storage + Edge Functions). Sin servidor propio que mantener.

Integridad y rendimiento

  • Primary keys: uuid default gen_random_uuid() en todas las tablas.
  • Foreign keys: reservations.customer_id → customers.id, reservations.vehicle_id/driver_id (nullable, ON DELETE SET NULL), drivers.vehicle_id (nullable), historial y logs con ON DELETE CASCADE hacia su reservación/actor.
  • Indexes: únicos en reservations.folio, vehicles.plate; búsqueda en customers.phone, customers.email; filtros frecuentes en reservations(date), reservations(status), reservations(created_by).
  • Timestamps: created_at/updated_at con default now() + trigger genérico set_updated_at() reutilizado en todas las tablas mutables.
  • Borrado: reservations y customers usan deleted_at (soft delete) en vez de DELETE real, para no romper reportes de ingresos históricos; "Eliminar" en la UI = admin marca deleted_at + registro en activity_logs.

Folio atómico

Un trigger BEFORE INSERT en reservations llama a una función SECURITY DEFINER que bloquea (SELECT … FOR UPDATE) la fila del año en folio_counters, incrementa y devuelve 'DT-' || año || '-' || lpad(numero, 6, '0'). Esto evita folios duplicados si dos usuarios crean tickets al mismo segundo — algo que un contador calculado en el frontend no puede garantizar.

RLS y políticas

  • RLS habilitado en todas las tablas, sin excepción.
  • Funciones auxiliares SECURITY DEFINER: is_admin() y can_edit_reservation(reservation_id), para no escribir subconsultas recursivas contra profiles dentro de cada política.
  • customers, vehicles, drivers: SELECT/INSERT/UPDATE para cualquier usuario autenticado; DELETE solo admin.
  • reservations: SELECT para autenticados; INSERT para autenticados; UPDATE permitido si is_admin() o si el perfil tiene permissions.can_edit_reservations = true; cancelar (cambiar a cancelled) solo admin; DELETE real bloqueado para todos (se usa soft delete, solo admin puede setear deleted_at).
  • reservation_status_history y activity_logs: INSERT solo vía trigger (no hay policy de insert para el rol autenticado); SELECT historial para todos, activity_logs solo admin.
  • settings: lectura para todos, escritura solo admin.

06Componentes clave

Ticket

  • TicketForm — react-hook-form + zod, secciones colapsables, campos de regreso condicionados a service_type === "redondo".
  • TicketPreview — réplica en HTML/Tailwind del layout del PDF; se re-renderiza en cada cambio del formulario (watch() de react-hook-form).
  • CustomerAutocomplete — busca por teléfono/email mientras se escribe; si no existe, lo marca como "cliente nuevo" para crearlo junto con la reservación.
  • TicketDocument (en /pdf) — la plantilla real de @react-pdf/renderer, independiente del preview visual.
  • ShareModal — enlace de WhatsApp/Email hacia el PDF ya subido a Storage.

Reservaciones y dashboard

  • ReservationsTable — tabla con orden, paginación y menú de acciones (ver/editar/PDF/compartir/duplicar/cancelar).
  • StatusBadge / StatusTimeline — pastilla de estado y línea de tiempo del historial.
  • RoleGate — oculta o deshabilita acciones según role/permissions del AuthContext (solo UX; la regla real vive en RLS).
  • StatCard, RevenueChart, UpcomingServices — bloques del Dashboard.
  • VehicleDriverSelect — filtra conductores por vehículo asignado y disponibilidad.

07Flujo para crear una reservación

sequenceDiagram
  participant U as Admin / Empleado
  participant F as TicketForm + TicketPreview
  participant D as Supabase (RPC create_reservation)
  participant P as TicketDocument (react-pdf)
  participant S as Storage (bucket tickets)

  U->>F: Completa datos (preview se actualiza en vivo)
  F->>D: RPC create_reservation(payload)
  D->>D: upsert customer + folio atómico + insert reservation + log de historial
  D-->>F: folio + reservation_id
  F->>P: arma TicketDocument con datos + folio + QR
  P-->>F: blob PDF (A4)
  F->>S: sube tickets/{folio}.pdf (registra en ticket_files)
  S-->>F: URL firmada
  F-->>U: ver / descargar / compartir + aparece en Reservaciones
  1. Captura y validación. zod valida en el cliente (teléfono, fechas, campos de regreso obligatorios solo si es redondo) antes de tocar la red.
  2. Transacción única en el servidor. Una función RPC de Postgres hace, en una sola transacción: buscar o crear el cliente por teléfono/email, asignar el folio, insertar la reservación y escribir el primer registro de reservation_status_history (pending). Si algo falla, no queda folio "quemado" ni cliente huérfano.
  3. Generación del PDF en el cliente. Con la respuesta (folio incluido) se construye TicketDocument y se genera el blob A4.
  4. Persistencia del PDF. El blob se sube a Storage y se referencia en ticket_files, para que "descargar" o "compartir" después no dependan de volver a generarlo.
  5. Retroalimentación. El usuario ve el ticket recién creado en el detalle y en el listado de Reservaciones, con estado Pendiente listo para pasar a Confirmado.

08Generación del PDF

Documento real construido con los primitivos de @react-pdf/renderer (Document, Page, View, Text, Image, Svg) — nunca html2canvas ni una captura del navegador.

  • Formato: A4, con una franja superior negro carbón + dorado (logo, "Danny Transfers", "Tulum Mexico") que retoma la identidad de referencia.png.
  • Cuerpo: tabla de pares etiqueta/valor tomada 1:1 de ticket-original.jpeg — Folio, Nombre, Pick Up, Room, Drop Off, Personas, Fecha, Hora, Teléfono, Email, Aerolínea, Vuelo — y un bloque de "Información de regreso" que solo aparece si service_type = redondo.
  • Precio y estado: precio con moneda formateada y una pastilla de estado con color semántico (verde solo si es positivo, como pediste).
  • QR: generado con la librería qrcode (data URL PNG) apuntando a la URL firmada del PDF en Storage o a la vista de detalle — se embebe como <Image>.
  • Pie de página: Meeting Point Tulum Airport, Meeting Point Cancún Airport, teléfono/redes de contacto y los términos básicos — leídos directamente de la tabla settings, no fijos en el código, para que Configuración los pueda editar sin tocar la plantilla.
  • Regenerar: vuelve a ejecutar el mismo generador con los datos actuales de la reservación y sube una nueva versión a ticket_files (se conserva el historial de versiones).
  • Compartir: enlace directo a la URL firmada del PDF vía WhatsApp (wa.me) o email.

09Roles y permisos

Dos capas: UX (oculta botones que el usuario no debería ver) y seguridad real (RLS en Postgres). La UX nunca es la única barrera.

AcciónAdminEmpleado
Crear reservaciones✓✓
Consultar reservaciones / generar PDF✓✓
Editar reservaciones✓Solo si permissions.can_edit_reservations
Cancelar reservaciones✓—
Eliminar (soft delete)✓—
Administrar clientes / vehículos / conductores✓Lectura + creación implícita al reservar
Administrar empleados (usuarios)✓—
Ver reportes / ingresos✓—
Configurar el sistema✓—

Implementación

  • Login: Supabase Auth (email + contraseña). Al confirmarse la sesión, se carga profiles (rol + permisos) en AuthContext.
  • Rutas: ProtectedRoute exige sesión; RoleRoute exige role === 'admin' para /usuarios, /reportes, /configuracion.
  • Componentes: <RoleGate allow={['admin']}> envuelve botones sensibles (cancelar, eliminar, editar sin permiso).
  • Alta de empleados: el admin llena un formulario; el frontend llama a la Edge Function create-employee, que verifica el JWT del llamante (debe ser admin) y recién ahí usa service_role del lado del servidor para crear el usuario en Auth y su profile. La service_role key nunca sale del entorno de la función.
  • Garantía real: aunque alguien manipule el frontend, las políticas RLS descritas en la sección 4 son las que aceptan o rechazan cada consulta en Postgres.

10Mejoras recomendadas

No reducen nada de lo que pediste; son adiciones para llevarlo de "funcional" a "profesional y sostenible".

Alta

Folio atómico por trigger + tabla contadorEvita duplicados o huecos en la numeración bajo uso concurrente, algo que calcular MAX(folio)+1 en el frontend no garantiza.

Alta

Historial de estado y actividad por trigger, no manualGarantiza una auditoría confiable de quién cambió qué y cuándo, requisito implícito de "historial" y "reportes".

Alta

Soft delete en reservaciones y clientesUn "Eliminar" real rompería reportes de ingresos históricos; se marca deleted_at y se oculta de las vistas normales.

Alta

Alta de empleados vía Edge FunctionEs la única forma de crear usuarios de Auth sin exponer la service_role key en el navegador.

Media

TanStack Query para el estado remotoCache, invalidación automática tras crear/editar/cancelar y menos código repetido de carga/error.

Media

Catálogos configurables (tipos de servicio, métodos de pago, puntos frecuentes)En vez de enums fijos en el código, quedan editables desde Configuración — pediste justamente un módulo de Configuración para esto.

Media

Versionado de PDFs en ticket_files"Regenerar" no debe perder el PDF anterior; útil si el cliente reclama un precio distinto al que recibió.

Media

Tipos generados desde Supabase (supabase gen types typescript)El esquema de la base de datos y los tipos de TypeScript nunca se desincronizan.

Media

Registro de tipo de cambio al crear la reservaciónSi en el futuro hay reportes en una sola moneda, el histórico no se distorsiona con el tipo de cambio actual.

11Próximos pasos

Con tu aprobación, el orden de construcción sería:

  1. Base del proyecto. Vite + React + TypeScript + Tailwind con los tokens de marca, estructura de carpetas y ruteo con guards.
  2. Supabase. Migraciones SQL (tablas, índices, RLS, triggers de folio/historial/updated_at), y conexión desde el frontend.
  3. Autenticación y roles. Login, AuthContext, ProtectedRoute/RoleRoute.
  4. Crear Ticket. Formulario + vista previa en vivo + RPC de creación.
  5. PDF. Plantilla TicketDocument, QR, subida a Storage.
  6. Reservaciones, Clientes, Vehículos, Conductores. Listados, filtros y CRUD.
  7. Dashboard y Reportes. Estadísticas, gráficas, ingresos.
  8. Usuarios y Configuración. Alta de empleados vía Edge Function, catálogos y datos de la empresa.
